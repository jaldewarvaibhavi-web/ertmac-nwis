# eRTMAC-NWIS — Nearby Wells Intelligence System (prototype)

**AI-powered offset-well knowledge and decision support for drilling operations**

> ## ⚠️ SYNTHETIC DATA — FOR PROTOTYPE DEMONSTRATION ONLY
> The Assam-style field, its reports and its "current well" stream are **generated**. They are
> **not Oil India data and not eRTMAC data**. One real, public drilling log (Utah FORGE 58-32, USA)
> is included for real-data testing and is labelled as such everywhere.

---

## 1. Problem
eRTMAC shows what is happening in the active well **now**. Knowledge of what happened in
**nearby wells** at the same depth and formation (losses, kicks, stuck pipe, cementing problems
and what fixed them) is scattered across daily drilling reports, well completion reports and
people's memory. Finding it takes time, so the same problems repeat.

## 2. Proposed solution
NWIS is a standalone decision-support platform alongside eRTMAC that keeps an institutional memory
and answers, for every bit position:

```
WHAT IS HAPPENING NOW?   -> current drilling parameters (eRTMAC-like stream)
WHERE AM I NOW?          -> depth + formation + metres below the formation top
WHAT HAPPENED BEFORE?    -> relevant offset wells and their historical events
WERE CONDITIONS SIMILAR? -> spatial + formation + depth + parameter + geology similarity
WHAT IS THE RISK?        -> Low / Moderate / Elevated risk INDICATION
WHY?                     -> evidence table with source documents + optional Claude explanation
ENGINEER DECISION        -> NWIS never controls equipment; the engineer decides
```

What makes it different from a generic map / chatbot / ML model:
1. spatially relevant offset wells, ranked by a transparent **5-part relevance score**;
2. **formation-aware** matching (events are compared by position *below the formation top*);
3. **depth-aware** correlation with a configurable tolerance (default ±25 m);
4. **institutional memory** extracted from reports by OCR + NLP, every fact with its source;
5. **current-vs-historical** parameter comparison (StandardScaler + Euclidean similarity);
6. **explainable** alerts ("Why?" + evidence + source reports);
7. **human-in-the-loop** (feedback buttons, decision note on every alert).

## 3. Architecture
```
 documents/ (DDRs: txt, PDF, scanned PDF) --OCR+NLP--> historical_events ─┐
 well_master, well_geology, formation_tops, historical_parameters ───────┼─> validation ─> SQLite (data/nwis.db)
 current_well_stream (synthetic eRTMAC-like) / FORGE log replay ─────────┘
                                   │
     geo_matching.py  radius + relevance score (spatial 30 · formation 20 · depth 20 · parameter 20 · geology 10)
     event_engine.py  formation-aligned event depths, status AT CURRENT DEPTH / AHEAD / PASSED
     similarity.py    current vs historical parameters and geology
     anomaly.py       current well vs its own recent normal (live signatures)
     risk_model.py    Random Forest where enough labels exist, leave-one-well-out validated
     explainability.py  risk indication + Why + evidence + historical mitigations
     rag.py           report retrieval + Claude explanation (grounded) with offline fallback
                                   │
            app/dashboard.py (Streamlit)        api/main.py (FastAPI)        run.py demo (terminal)
```

## 5. Synthetic-data limitations
* All synthetic events and their signatures were generated by our own rules, so models partly
  re-learn the generator. **All metrics are "Prototype validation only — not representative of
  field deployment accuracy."**
* Porosity, caliper, ECD and gas are synthetic; on the real FORGE well they show "Not available".
* The FORGE well has no labels and no neighbours: only live anomaly detection runs on it.

## 11. ML methodology
* **Offset relevance** — transparent weighted score, not ML (formulas in `src/similarity.py`).
* **Parameter similarity** — StandardScaler fitted on historical offset data; similarity
  `1 / (1 + d/√k)`, d = Euclidean distance of standardised vectors, k = parameters available in both.
* **Live anomaly detection** (`anomaly.py`) — each reading vs the well's own previous ~30 m in the same
  formation (rules: flow-out/pit → losses/kicks, torque ratio, pressure vs pump rate, ROP per WOB) +
  Isolation Forest score; overlapping signals merged into incidents with confidence.
* **Risk model** (`risk_model.py`) — Random Forest per event type, target "this event type starts
  within the next 200 m", features: offset evidence, formation, metres below top, porosity, caliper,
  drilling parameters. **Trained only where ≥ 8 events in ≥ 5 wells exist**; other types:
  *"Insufficient labeled data for reliable ML training."*
* **Risk indication** = offset evidence × proximity × condition similarity, raised by a matching
  live signature, averaged with the ML score only if that model passed validation. Wording is
  always "Low / Moderate / Elevated risk indication" — never "will occur".

## 12. Validation methodology
Leave-one-well-out: 15 folds; in each, the held-out well's data **and its events** are removed from
training *and* from the offset-evidence features of the training wells (tested in
`tests/test_risk_and_explain.py`). Metrics pooled over all folds, threshold 0.5.
**Prototype validation only — not representative of field deployment accuracy.**

| Event type | Status | Precision | Recall | F1 | ROC-AUC | PR-AUC | FPR | FNR | Evidence-only baseline F1 | Events warned in advance |
|---|---|---|---|---|---|---|---|---|---|---|
| Mud Loss | trained, **passed** gate → used | 0.44 | 0.67 | 0.53 | 0.95 | 0.40 | 0.06 | 0.33 | 0.58 | 15/15 (median 182 m ahead) |
| Wellbore Instability | trained, **failed** gate → not used | 0.07 | 0.07 | 0.07 | 0.80 | 0.11 | 0.04 | 0.93 | 0.00 | 6/11 |
| Torque Spike, Bit Problem, Kick, Stuck Pipe, Cementing | Insufficient labeled data for reliable ML training | – | – | – | – | – | – | – | – | – |

Honest reading: for mud loss the **offset-evidence rule alone is as good as the ML model** (F1 0.58 vs
0.53) and the most important model feature is offset evidence — the institutional memory is what
carries the prediction. Report-reading accuracy: 44/44 events from 74 synthetic reports (incl. 4 via OCR);
the reports were generated for this test, so this is an easy test.
Test suite: `python run.py test` (29 tests; FastAPI endpoint test runs when FastAPI is installed).

## 13. Claude integration
Claude is the **explanation layer, not the risk model**. The deterministic pipeline produces a
structured evidence object (depth, formation, risk level, components, supporting wells with sources,
historical mitigations); Claude receives only that plus retrieved report excerpts, with a system
prompt that forbids adding facts, requires citations, forbids "will occur" and operational
instructions, and requires *"Insufficient historical evidence."* when appropriate. Every Claude
answer is checked: if it mentions a well that is not in the evidence it is rejected and the
deterministic answer is shown. Without `ANTHROPIC_API_KEY` the app runs fully offline with the
deterministic explanations.

## 14. Limitations
* Synthetic field; relevance weights, thresholds and look-ahead are prototype choices.
* Rule-based report extraction is tuned to three writing styles; real reports need broader rules or an
  LLM extractor with engineer review (the `/documents/ingest` endpoint returns events for review, it does
  not auto-insert them).
* Risk scores are indications, not calibrated probabilities.
* TF-IDF retrieval by default (offline); ChromaDB embeddings optional.
* Single-user SQLite; no authentication.
